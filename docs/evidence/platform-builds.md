vendoring them would bloat the repo without adding verifiability. The
durable record is the run id (linkable forever), the head SHA it ran, and
what it proved — tabulated here from `docs/platform-enablement-review.md`.
Accepted by #205; the #205 closing overclaim is corrected by that issue's
follow-up comment, and the Windows park by ADR 0009 (superseded 2026-09-23;
see the revalidation rows below).

Legacy floor-12 legs (`macos-intel_legacy`, `macos-apple-silicon_legacy`)
did not run here: the per-architecture proof above plus the documented
flavor difference (same builders, PySide6 6.9.3 overlay with
`WAVES_MACOS_MIN=12.0`) is the coverage the issue's alternative permits.
A release cut builds all eight legs including legacy by the
all-platform guard, so legacy evidence arrives with the first release.

Reading note (historical — the workflow has since changed): at the time of
runs `34929398611` (11/13 skipped incl. Check out and Build) and
`35019374456` (12/14 skipped) the `only` filter still created every matrix
job, so legs it excluded finished "success" with their build steps skipped
and the macOS legs proved nothing — job conclusions, not builds. Since #244
the filter selects legs up front, so every conclusion in the newer rows
means a real build. Local macOS build evidence since comes from
#243 (cold 76 m 33 s, darwin/arm64) and #245 (385 s with the
`lazy_extractors` exclusion); the Windows revalidation on that recipe
landed with run `35836125855` (2026-09-23, both legs green), and ADR 0009
is superseded. The Windows legs' applicable steps are build plus
smoke-launch (x64) and build (arm64): the macOS floor assert is
macOS-only and does not apply to them.
