# ALAC corruption from Apple Music: root cause, verification, and what Waves must build

Research for [wayfinder ticket #5](https://github.com/ranokay/waves/issues/5). Investigated 2026-09-01 against primary sources: the [ALAC Verification Guide](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/) (read via [Wayback snapshot](http://web.archive.org/web/20260516013029/https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/) — the site's TLS chain fails local verification) and the [original 2025-08-28 announcement](https://channel.0w0.best/posts/6294) it expands on, FFmpeg's ALAC decoder source, and shallow-clone greps + issue/PR/commit archaeology of all three candidate engines. No code was copied.

## Bottom line

**Since ~May 2025, some Apple Music lossless (ALAC) streams are corrupt at the source: Apple's own encoder emits malformed ALAC packets (missing `TYPE_END` terminators) plus sample-level audio errors. This is provably not a downloader bug — the same corruption survives loopback recording of the official Windows client — and it is still unfixed as of the blog's 2026-03-17 retest and July/August 2026 engine issues. Any engine Waves picks will download these bad bytes; the difference is detection.** AppleMusicDecrypt v2 is the only candidate with an always-on, per-song integrity check (full ffmpeg decode, empty stderr = pass) plus a documented Apple-side-cause troubleshooting entry; v3's rewrite replaced it with a weaker container-structure check that cannot catch this; zhaarey's downloader has an opt-in conversion-time stderr check and a default-off ALAC packet patcher; gamdl has no verification at all and currently ships silent corruption to its users ([#344](https://github.com/glomatico/gamdl/issues/344)). Waves must build its own post-download ffmpeg decode-to-null check (~milliseconds of CPU per track, no network), retry to distinguish transient session failures from bad Apple sources, and quarantine persistently-bad tracks instead of silently saving them.

## Root cause

- **What broke and when**: "After around May of this year, the lossless music encoder on some Apple Music node appears to have broken … the music source files they serve are themselves corrupt, with missing samples compared to other sources" — [original announcement, 2025-08-28](https://channel.0w0.best/posts/6294). Affected files carry an `Encoded date` (ffmpeg `creation_time`) after ~2025 — e.g. the blog's example shows `creation_time : 2025-06-23T04:06:21Z` ([blog](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)).
- **It is Apple's source, not the download path**: the blog's loopback methodology — record the official Apple Music Windows client through a bit-exact loopback channel (with Windows' `CAudioLimiter` disabled, sample rate/bit depth matched) — first proves the recording chain is faithful by binary-matching a known-good track (decrypted ALAC ≡ MORA-purchased FLAC via foobar2000 Binary Comparator; recorded WAV ≡ same FLAC after offset alignment), then shows the known-bad JOLIN Tsai "Pleasure" track still contains the stray sample when loopback-recorded from the official client, while the same track purchased from Tidal and Amazon Music HD is clean and identical ([blog, 验证/内录与验证/问题专辑 sections](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)). Community conclusion: the corruption is embedded in Apple's lossless streams; third-party tools merely faithfully deliver it.
- **The packet-level defect**: Apple's encoder emits ALAC packets that are "missing a `TYPE_END` terminator … The algorithm locates each such packet and appends `TYPE_END` so that FFmpeg's decoder can parse the file correctly" — [zhaarey PR #109, "ALAC files fixing"](https://github.com/zhaarey/apple-music-downloader/pull/109). In the bitstream, the decoder reads a 3-bit element type per block; `TYPE_END` = 7 and `TYPE_DSE` = 4 ([FFmpeg `libavcodec/alac_data.h`](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/alac_data.h)). Without the terminator, FFmpeg's `alac_decode_frame` keeps parsing past the element body, hitting garbage — "invalid element channel count" (`AVERROR_INVALIDDATA`) or an unimplemented element — "Syntax element %d" (`AVERROR_PATCHWELCOME`, rendered as "Not yet implemented in FFmpeg, patches welcome") — and drops the whole packet ([FFmpeg `libavcodec/alac.c`, `alac_decode_frame`](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/alac.c)): a 4096-sample block vanishes, which is exactly the "one sample error grows into a 4096-sample block error" observation in the [blog](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/).
- **Sample-level damage exists beyond the packet framing**: on the bad Safari track, Adobe Audition phase-cancellation against the clean Amazon/Tidal versions reveals an isolated stray sample in the right channel ([blog, 问题专辑](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)); PR #109 likewise concedes the corruption "is present from the very beginning … Playing such a track in Apple Music on a MacBook with the latest macOS still produces the same minor byte-level losses. QuickTime simply ignores the malformed packets" ([zhaarey PR #109](https://github.com/zhaarey/apple-music-downloader/pull/109)). So a parseable file is not automatically a clean file.
- **Which paths are affected**: all paths that deliver Apple's ALAC stream — every third-party tool and Apple's own client (the loopback test is the proof). Apple's AVFoundation/QuickTime and BASS-based players (MusicBee, fre:ac) tolerate the malformed packets; ffmpeg-based players/converters and foobar2000's integrity check surface them ([wrapper #51 discussion](https://github.com/WorldObservationLog/wrapper/issues/51), [gamdl #337](https://github.com/glomatico/gamdl/issues/337)). AAC downloads are not implicated ("the normal apple AAC files are completely fine" — [wrapper #51](https://github.com/WorldObservationLog/wrapper/issues/51)); the guide and its examples are lossless-only.
- **Status**: still broken. Blog update 2026-03-17: retest of [TOGENASHI TOGEARI - Fragile Violet - Single](https://music.apple.com/cn/album/fragile-violet-single/1820118990) still fails to decode and the `Encoded date` is unchanged (2025-06-23), i.e. Apple has not re-encoded ([blog](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)); fresh reports continue in [AppleMusicDecrypt #121](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/121) (2026-05, maintainer's entire reply is a link to this guide), [gamdl #337](https://github.com/glomatico/gamdl/issues/337) (2026-07) and [gamdl #344](https://github.com/glomatico/gamdl/issues/344) (2026-08).
- **Known-bad albums for testing**: [TOGENASHI TOGEARI - Fragile Violet](https://music.apple.com/cn/album/fragile-violet-single/1820118990), [Nate Sib - for us](https://music.apple.com/cn/album/for-us/1811381025), [JOLIN Tsai - Pleasure](https://music.apple.com/jp/album/pleasure/1827894274) ([blog](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)).

## Verification method

- **The guide's procedure** ([blog, 现象 + 速查工具](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)): decode the .m4a with ffmpeg to raw PCM and inspect stderr for these strings: `Invalid data found when processing input`, `Not yet implemented in FFmpeg`, `Syntax element`, `patch welcome`/`patches welcome`. Canonical command (Windows form; `-f wav NUL`, Bash uses `-f null -`): `ffmpeg -i "file.m4a" -f wav -hide_banner -loglevel info NUL 2>&1`. Any hit = corrupted. The blog ships batch/Bash/PowerShell scanners built on exactly this ([blog, 附录](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)). Corroborating checks: foobar2000 integrity verification fails ("Reported length is inaccurate" — [announcement](https://channel.0w0.best/posts/6294)), foobar2000 FLAC conversion errors, and a risk pre-filter on `Encoded date` ≥ 2025.
- **Why stderr-sniffing works**: those strings are FFmpeg's ALAC decoder erroring out mid-decode ([`libavcodec/alac.c`](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/alac.c)); a full decode without stderr output means every packet parsed.
- **Fully programmatic as a post-download check**: yes — this is precisely what AppleMusicDecrypt v2 does internally: `check_song_integrity()` runs `ffmpeg -y -v error -i <file> -c:a pcm_s16le -f null /dev/null` and passes iff stderr is empty ([v2 `src/mp4.py:271`](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v2/src/mp4.py)). `-v error` + `-f null` is the minimal form: no WAV output, errors only on stderr.
- **Cost**: negligible. The blog's worked example decodes a 3:07 track at ~3.5×10³× realtime (~0.05 s elapsed) ([blog example output](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)); `-f null` skips disk writes; purely local CPU, no network. Trivially parallelizable per download.
- **Limitation** (the guide's own caveat): a pass is not a guarantee — the method "can effectively identify and exclude some problematic albums, but cannot guarantee that albums which pass verification are error-free"; the only complete check is cross-referencing another trusted lossless source (e.g. MD5 of the decoded stream), and the author's cross-checks found no loudness-matched-but-different-MD5 cases ([blog, 结语](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)).

## Exposure of each candidate engine

- **AppleMusicDecrypt v2 (default branch) — best covered.** Every song is integrity-checked post-decrypt via the ffmpeg decode-to-null above ([v2 `src/rip.py:195-203`](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v2/src/rip.py)); `failedSongNotPassIntegrityCheck = false` (default) warns and saves anyway, `true` fails the task and does not save ([v2 `config.example.toml:50-53`](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v2/config.example.toml) — "Due to the possibility of source file corruption, open with caution"). The README documents both failure causes — transient wrapper decryption errors that "usually disappear after a few days" vs. "the audio source file provided by Apple Music is damaged", with the announcement link — ([README "Song did not pass the integrity check"](https://github.com/WorldObservationLog/AppleMusicDecrypt#song-did-not-pass-the-integrity-check)). The mechanism predates the 2025 outbreak as a defense against truncated decodes ([#20](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/20): "intended to prevent the script from saving corrupted audio files"); #69's blanket failures were a wrapper-manager bug, fixed in [wrapper-manager `cb83d13`](https://github.com/WorldObservationLog/wrapper-manager/commit/cb83d132b5a95240cb52f4706e75e061bf428539); the maintainer explicitly attributes the Apple-source class to Apple ([wrapper #51](https://github.com/WorldObservationLog/wrapper/issues/51): "a known issue and it was caused by Apple, not the wrapper", and [#121](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/121) links this guide).
- **AppleMusicDecrypt v3 (rewrite) — regression.** `check_song_integrity` is now a "pure-Python structural integrity check: the output file must parse as a valid fragmented MP4 (init + >=1 fragment)" ([v3 `src/rip.py:779`](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/src/rip.py)) — it never decodes the ALAC payload, so it catches truncated/malformed containers but **not** the Apple-source packet corruption, which is invisible at container level. v3 keeps the same config knobs (`retryTime`, `failedSongNotPassIntegrityCheck`) and adds byte-range resume from box boundaries ([v3 `src/rip.py` download loop](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/src/rip.py)), but Waves would need to re-add a decode-level check.
- **zhaarey/apple-music-downloader — opt-in, conversion-coupled, plus a patcher.** No verification runs by default. `convert-check-bad-alac: true` captures ffmpeg stderr during ALAC→X conversion; on any output it prints "Detected ALAC Error." and, with `convert-delete-bad-alac: true`, deletes the converted file, keeps the m4a, and writes stderr to a `.log` ([`main.go:791-820`](https://github.com/zhaarey/apple-music-downloader/blob/main/main.go), flags in [`structs.go:57-59`](https://github.com/zhaarey/apple-music-downloader/blob/main/utils/structs/structs.go); added 2026-01-22, commit [`58f4ded7`](https://github.com/zhaarey/apple-music-downloader/commit/58f4ded7)). If you keep ALAC and never convert, nothing is checked. Separately, `alac-fix: true` (default off) runs the [PR #109](https://github.com/zhaarey/apple-music-downloader/pull/109) `alacfix` bitstream patcher after saving ([`main.go:1099`](https://github.com/zhaarey/apple-music-downloader/blob/main/main.go), [`utils/alacfix/alacfix.go`](https://github.com/zhaarey/apple-music-downloader/blob/main/utils/alacfix/alacfix.go), standalone CLI in [`cmd/alacfix`](https://github.com/zhaarey/apple-music-downloader/tree/main/cmd/alacfix)) — it appends the missing `TYPE_END` so ffmpeg can decode, but the author notes it "does not make things worse; it only makes the files readable by FFmpeg", i.e. the embedded sample losses remain. Its issue tracker shows no corruption discussion at all (searches for integrity/check/ALAC return nothing). **License note: the repo has no LICENSE file** (GitHub API reports none) — the algorithm may be cited, not copied.
- **gamdl — completely exposed.** No integrity/verification feature exists anywhere in the codebase (grep of a current shallow clone: zero hits for integrity/verify; ffmpeg is used only for remux). Its tracker instead documents corruption on both axes: downloader-side session corruption — files with no metadata/no audio after ~50-100 songs in a batch, still open ([#328](https://github.com/glomatico/gamdl/issues/328), [#344](https://github.com/glomatico/gamdl/issues/344): "of 2400 I had download only around 900 … weren't corrupted", same songs succeed on later attempts) — and the Apple-source ALAC skips, where a reporter measured ffmpeg's decode coming up ~24,576 samples (6×4096 blocks) short of fre:ac's decode of the same file ([#337](https://github.com/glomatico/gamdl/issues/337), open, maintainer engaged, unresolved). No reference to the hanlin guide anywhere in gamdl's tracker. MIT-licensed, so the gap is fixable but is not fixed.

## What Waves must build

1. **A mandatory post-download verification step** (engine-agnostic, in Waves' downloader shell, not inside any engine): after download+decrypt+tag, run `ffmpeg -v error -hide_banner -nostdin -i <file.m4a> -map 0:a:0 -c:a pcm_s16le -f null -` and treat a non-empty stderr as failure; optionally match the guide's five strings for log classification ([method](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/), [AMD v2 implementation](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v2/src/mp4.py)). This must wrap whichever engine wins the choice, including AppleMusicDecrypt v3 whose structural check is insufficient ([v3 `rip.py:779`](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/src/rip.py)).
2. **Cost**: ~milliseconds of CPU per track (observed ~3500× realtime decode, `-f null`, no network) — acceptable to run on every download with no throttling ([blog](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)). Cheap enough to also run at library-import time as a second pass.
3. **A risk pre-filter**: parse `creation_time`/Encoded date from the container; ≥2025-05 flags the track as outbreak-era for stricter handling ([blog](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/), [announcement](https://channel.0w0.best/posts/6294)).
4. **Refetch/rollback policy with two failure classes**:
   - *Transient (session/decrypt)*: a fresh download of the same track passes — evidenced by [AMD #54](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/54) (integrity failures succeed on retry) and the wrapper-manager fix for [#69](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/69). Policy: on verification failure, delete the artifact, re-download up to N times (AMD uses `retryTime = 8` for download retries — [v2 config](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v2/config.example.toml)); pass → keep.
   - *Persistent (Apple source)*: re-download returns the same corrupt bytes — Apple has not re-encoded affected tracks (2026-03-17 retest, unchanged Encoded date — [blog](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)). Policy: after N consecutive failures for the same track id, **quarantine**: do not place the file in the library, mark the track/album as corrupt-source in the DB, persist a skip-list, and surface it in the UI rather than saving silently. Never adopt AMD v2's default warn-and-save posture ([v2 config comment](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v2/config.example.toml)) — gamdl's no-check behavior shows the end state: users accumulate thousands of corrupt files ([#344](https://github.com/glomatico/gamdl/issues/344)). Re-check skip-listed tracks periodically in case Apple re-encodes (detectable via the Encoded date changing). **[Overruled by the spec, §6.3: no background re-checking — the skip-list recovers only through the explicit REDOWNLOAD re-ask, which re-attempts and clears the entry when Apple's re-encode verifies.]**
5. **No silent transcoding of flagged files**: the guide explicitly warns that ALAC files — and especially files already transcoded to FLAC — are latent contamination, because tolerant decoders mask the errors ([blog, 结语](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)); fre:ac/MusicBee playing a file "fine" proves nothing ([gamdl #337](https://github.com/glomatico/gamdl/issues/337)). Waves must not convert before verification passes.
6. **No TYPE_END patching in v1**: the only known patcher lives in an unlicensed repo (no copying), and patching converts an undecodable file into a decodable-but-still-lossy one, defeating verification — it masks a bad source instead of refetching it ([PR #109](https://github.com/zhaarey/apple-music-downloader/pull/109), [alacfix](https://github.com/zhaarey/apple-music-downloader/blob/main/utils/alacfix/alacfix.go)). Revisit only as an explicitly-labeled salvage feature later.
7. **Honest limits in the spec**: verification proves ffmpeg-decodability, not bit-perfect fidelity — the only full guarantee is cross-source comparison, which Waves cannot automate against other paid services ([blog caveat](https://blog.hanlin.press/2025/09/ALAC-Verification-Guide/)). Document this in the QA requirement.
