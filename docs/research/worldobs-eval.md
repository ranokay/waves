# Evaluating WorldObservationLog/wrapper + AppleMusicDecrypt as Waves' Apple Music engine

Research for [wayfinder ticket #4](https://github.com/ranokay/waves/issues/4). Investigated 2026-09-01 against primary sources: shallow clones of all four branches (wrapper `lite`/`main`/`arm64`, AppleMusicDecrypt `v2`/`v3`), their code/READMEs/licenses, and the full open+closed issue/PR lists of both repos. No code was copied.

## Bottom line

**Yes, with conditions — this is the right engine family to wrap, and the `wrapper` `lite` branch + AppleMusicDecrypt `v3` branch are the specific artifacts to target.** It is the actively maintained, license-clean descendant of the zhaarey lineage, covers every settled Waves constraint (ALAC hi-res, independently selectable Dolby Atmos, lyrics in all formats including word-timed/translations, 5000×5000 cover art, one-time login), and v3's architecture (JSON-HTTP wrapper sidecar + local Rust decryption + pure-Python MP4 muxing) is the most embeddable shape of any Apple engine we evaluated. Conditions: Waves must (a) supply its own search layer (the engine has none), (b) survive long-batch Apple throttling by restarting the wrapper sidecar, and (c) accept that on macOS Apple silicon the decryption core runs emulated (x86-64 Android code under QEMU/Docker), which is the platform with the most open friction.

## What "wrapper" actually is

- The default branch is **`lite`** ("wrapper-lite"): a single-port C/C++ HTTP server exposing six JSON endpoints — `/m3u8`, `/key`, `/lyrics`, `/license`, `/webplayback`, `/status` ([README, lite branch](https://github.com/WorldObservationLog/wrapper/blob/lite/README.md)). It is not a Tidal-style CLI; it is a local **API sidecar** that a downloader client talks to.
- What it wraps: **Apple's own Android client libraries**. `lite` dlopen/links `storeservicescore`/`mediaplatform` symbols from `com.apple.android.music` (e.g. `_ZN17storeservicescore10URLRequest...` in [`lite/tokens.cpp`](https://github.com/WorldObservationLog/wrapper/blob/lite/lite/tokens.cpp)) and spoofs the Android Music app device identity `Music/5.0.2/Android/10/Pixel 8/...` ([device-info section](https://github.com/WorldObservationLog/wrapper/blob/lite/README.md#device-info)). That is why it can mint real Apple tokens and speak the real playback APIs: dev token from `sf-api-token-service.itunes.apple.com/apiToken` (`clientId=musicAndroid`), music user token from `play.itunes.apple.com/WebObjects/MZPlay.woa/wa/createMusicToken` ([tokens.cpp:66-171](https://github.com/WorldObservationLog/wrapper/blob/lite/lite/tokens.cpp)), and HLS m3u8 via `play.music.apple.com/WebObjects/MZPlay.woa/wa/webPlayback` with `Authorization: Bearer <devToken>` + `X-Apple-Music-User-Token` ([apple_api.cpp:296-330](https://github.com/WorldObservationLog/wrapper/blob/lite/lite/apple_api.cpp)).
- Why it exists: FairPlay decryption keys for streaming HLS can only be obtained through Apple's first-party client stack, so the sidecar borrows the Android app's trusted code path and re-exposes it as plain HTTP for third-party downloaders (originally zhaarey's architecture; the old README credits "Anonymous, for providing the original version … and the legacy Frida decryption method" — [arm64 README](https://github.com/WorldObservationLog/wrapper/blob/arm64/README.md)).
- Deployment model: the recommended launcher boots a **self-contained QEMU guest** (Android-ish Linux rootfs) and forwards the HTTP API to the host — "no rooted device or chroot required"; accel options kvm/hvf/whpx/tcg; Docker mode also exists ([README, Run with QEMU](https://github.com/WorldObservationLog/wrapper/blob/lite/README.md#run-with-qemu-recommended)).

### What the arm64 branch changes

- `arm64` is the **old two-port C architecture** (`main.c`/`wrapper.c`/`import.h` Frida-style hooks; decrypt port 10020 + m3u8 port 20020 — [arm64 README](https://github.com/WorldObservationLog/wrapper/blob/arm64/README.md)), vs `main` which is the same old arch but x86_64-only ([main README](https://github.com/WorldObservationLog/wrapper/blob/main/README.md)). The `arm64` branch adds **Linux arm64 support** (credited to "chocomint" in the README), an Android/Termux packaging target ([`wrapper-android.c`](https://github.com/WorldObservationLog/wrapper/blob/arm64/wrapper-android.c), [build-for-arm64.yml](https://github.com/WorldObservationLog/wrapper/blob/arm64/.github/workflows/build-for-arm64.yml)), and Android/Termux fixes as recently as 2026-08-05 (branch commits via API).
- **The old branches carry no LICENSE file** (verified: no `LICENSE*` in `main` or `arm64` working trees; the API reports license only via the repo's lite default). Only `lite` ships an [MIT LICENSE](https://github.com/WorldObservationLog/wrapper/blob/lite/LICENSE) ("MIT License … Copyright (c) 2026 WorldObservationLog"). For Waves this means: build on `lite`, and do not copy code from `main`/`arm64`.
- The old branches are also superseded by the ecosystem: AppleMusicDecrypt v3 speaks only the lite HTTP API ([v3 README "About V3"](https://github.com/WorldObservationLog/AppleMusicDecrypt/tree/v3)); v2 speaks gRPC to old-arch wrapper / wrapper-manager ([v2 README "About V2"](https://github.com/WorldObservationLog/AppleMusicDecrypt#about-v2)).

## What AppleMusicDecrypt is, what v3 changes, and how they relate

- **AppleMusicDecrypt** is a Python 3.11+ interactive downloader (AGPL-3.0, 642 stars) "inspired by [zhaarey/apple-music-alac-atmos-downloader](https://github.com/WorldObservationLog/AppleMusicDecrypt#apple-music-decrypt)". It parses Apple Music URLs (song/album/artist/playlist links), pulls metadata from Apple's catalog API, fetches HLS playlists from the wrapper, and downloads + decrypts + tags output files. Default branch is `v2` (gRPC to wrapper/wrapper-manager); **`v3`** is a rewrite ([v3 README](https://github.com/WorldObservationLog/AppleMusicDecrypt/tree/v3)).
- **v3 changes** ([v3 README "About V3"](https://github.com/WorldObservationLog/AppleMusicDecrypt/tree/v3)):
  - **HTTP instead of gRPC** — client ↔ wrapper-lite over plain JSON (`/m3u8 /key /lyrics /webplayback /license /status`; client binding in [`src/wrapper.py`](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/src/wrapper.py)).
  - **Local streaming decryption** — the key template is fetched once per song from `/key` and every sample is decrypted locally by the bundled [`temari`](https://github.com/WorldObservationLog/Temari) Rust library ("Apple Music FairPlay Streaming decryption library", MIT) while the file downloads — no per-sample wrapper round-trips ([v3 `src/decrypt.py`](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/src/decrypt.py)).
  - **Zero external binaries** — pure-Python ISO-BMFF parse/decrypt/re-encapsulate ([`src/mp4.py`, `src/mux.py`]), tags via `mutagen`, structural integrity check ([`rip.py:779 check_song_integrity`](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/src/rip.py)).
  - Music-video downloads (pure-Python Widevine CBCS), byte-range resume, prefetch/batch, full-screen TUI with `--legacy-ui` fallback.
  - Relationship to wrapper: **login lives on the wrapper side** (`lite --login user:pass`), not in the downloader; v3 can also spawn wrapper-lite locally via the QEMU launcher (`[localInstance]`, experimental) ([v3 README "Run"](https://github.com/WorldObservationLog/AppleMusicDecrypt/tree/v3#run), [config.example.toml](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/config.example.toml)).

## Auth + decryption requirements

- **One-time login, then token caching** — `lite --login user:pass` (+ 2FA: interactive prompt, or `--code-from-file data/2fa.txt`) caches `STOREFRONT_ID` / `MUSIC_TOKEN` / `DEV_TOKEN` to the data dir and background-refreshes every 1800 s ([README lite args](https://github.com/WorldObservationLog/wrapper/blob/lite/README.md#lite-arguments), [`tokens.cpp:224-279 refresh_tokens`](https://github.com/WorldObservationLog/wrapper/blob/lite/lite/tokens.cpp)). The downloader never sees credentials. This matches Waves' "one-time external setup is acceptable" constraint.
- **Materials needed**: an Apple ID **with an active Apple Music subscription** ("An active subscription is still needed" — [arm64 README](https://github.com/WorldObservationLog/wrapper/blob/arm64/README.md)); the wrapper guest ships Apple's Android app libraries and device identity; per-account stable Android ID derived from a username hash ([README device-info](https://github.com/WorldObservationLog/wrapper/blob/lite/README.md#device-info)). No manually-extracted tokens/certs required.
- **Platform support**:
  - **macOS Apple silicon**: no native binary — the guest rootfs Android libs are **ELF x86-64** (`file rootfs/system/lib64/libgui.so` → "ELF 64-bit … x86-64"; CMake targets `x86_64-linux-android` — [CMakeLists.txt](https://github.com/WorldObservationLog/wrapper/blob/lite/CMakeLists.txt)), so on Apple silicon it runs under QEMU TCG or Docker `linux/amd64`+Rosetta. This is the roughest platform: open issue [#61 "qemu signal 11 crash after 2FA submission on Apple Silicon (linux/amd64)"](https://github.com/WorldObservationLog/wrapper/issues/61) (Docker Desktop + Rosetta, M2). CI does build `linux-aarch64` host packages (i.e., an arm64 host running the x86-64 guest) — [build-lite.yml matrix](https://github.com/WorldObservationLog/wrapper/blob/lite/.github/workflows/build-lite.yml).
  - **Windows/Linux x86_64**: the mainstream path — QEMU with whpx/kvm accel, or Docker; Windows pre-configured AMD builds are published per release workflow ([v3 README "Run"](https://github.com/WorldObservationLog/AppleMusicDecrypt/tree/v3#run)). The v3 downloader itself is pure Python and runs natively on macOS arm64.
- Decryption itself: FairPlay template+sample decryption via Temari locally (ALAC/EC-3/AAC-HLS); `aac-legacy` (non-lossless stereo) uses Widevine with a bundled `assets/device.wvd` and pywidevine license via wrapper `/license` ([v3 `decrypt.py` header](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/src/decrypt.py), [assets/device.wvd](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/assets/device.wvd)).

## Audio quality tiers and independent Dolby Atmos

- Codec tiers ([v2/v3 README "Support Codec"](https://github.com/WorldObservationLog/AppleMusicDecrypt/tree/v3#support-codec)): `alac` (audio-alac-stereo, lossless up to 24-bit/192 kHz — caps configurable via `maxSampleRate=192000`/`maxBitDepth=24`), `ec3` (**audio-atmos / audio-ec3**), `ac3` (audio-ac3), `aac` (audio-stereo), `aac-binaural`, `aac-downmix`, `aac-legacy` (non-lossless).
- **Atmos is independently fetchable**: codec is a first-class CLI choice (`dl -c ec3 …`) and the default priority list is `["alac", "ec3", "ac3", "aac"]` with `codecAlternative` fallback and `atmosConventToM4a = true` (encapsulate Atmos as M4A + write tags) — [config.example.toml](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/config.example.toml). A `quality`/`qa` command tabulates each rendition's bitrate/channels/sample-rate/bit-depth from the m3u8 ([`src/quality.py`](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/src/quality.py)). Atmos is delivered as EC-3 JOC; the maintainer demonstrated full Atmos via ffprobe `"eac3 (Dolby Digital Plus + Dolby Atmos) … 5.1(side) … 768 kb/s"` in [#30](https://github.com/WorldObservationLog/wrapper/issues/30).

## Lyrics and cover art

- **Lyrics**: wrapper `/lyrics?adamId=…&language=…&syllable=…` proxies Apple's lyric APIs — `syllable-lyrics` (word-timed/karaoke TTML) or `lyrics` (line-timed TTML, plain-text fallback) ([apple_api.cpp:224-287](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/src/rip.py); [wrapper README endpoint table](https://github.com/WorldObservationLog/wrapper/blob/lite/README.md#http-api)). v3 config covers everything Waves wants: `saveLyrics`, `lyricsFormat = "lrc" | "ttml"`, `lyricsSyllable` (word-timed), `lyricsExtra = ["translation", "pronunciation"]`, plus lyrics embedded in tags ([config.example.toml](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/config.example.toml)).
- **Cover art**: `saveCover = true`, `coverFormat = "jpg"`, `coverSize = "5000x5000"` — the Apple artwork URL template is requested at 5000×5000, i.e., original/highest resolution, saved standalone and embedded as the `covr` atom ([config.example.toml](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/config.example.toml), [`metadata.py:143 cover_url=attributes.artwork.url`](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/src/metadata.py)). No artwork-related bugs found in either tracker (the metadata PR churn is around IDs/ISRC/rating tags: [#56](https://github.com/WorldObservationLog/AppleMusicDecrypt/pull/56), [#51](https://github.com/WorldObservationLog/AppleMusicDecrypt/pull/51), [#65](https://github.com/WorldObservationLog/AppleMusicDecrypt/pull/65)).

## Search capability

- **None.** Both v2 and v3 are URL/ID-driven only: song/album/artist/playlist share links (+ `get_album_by_upc`); the catalog client has no search method ([`src/api.py` method list](https://github.com/WorldObservationLog/AppleMusicDecrypt/blob/v3/src/api.py); a repo-wide grep for `search` finds only regex/URL code). Waves must build its own search layer — e.g., the public unauthenticated iTunes Search API, or the Apple catalog API using the wrapper's cached music token.

## Notable issues/PRs (corrupted ALAC, Atmos, lyrics, artwork)

- **Corrupted ALAC / integrity check**: a recurring theme on the v2-era stack — [#53](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/53) (every track fails integrity, Windows), [#58](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/58) (first ~13 s audio, then silence — wrapper decryption error), [#43](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/43), [#63](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/63), [#69](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/69), [#54](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/54) (retry request), [#121](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/121) (single corrupted frame at 194.9 s), [#60](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/60) (some JP files never decrypt), [#95](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/95) (50 KB/s decrypts). The FAQ attributes these to (1) transient wrapper decryption bugs that "usually disappear after a few days" or (2) Apple-side source damage ([v3 FAQ](https://github.com/WorldObservationLog/AppleMusicDecrypt/tree/v3#faq), ref [t.me/abcthoughts/6294](https://t.me/abcthoughts/6294)); v3 adds a structural integrity check and `failedSongNotPassIntegrityCheck` config, plus a documented benign "bit depth doesn't match codec" case (Apple mis-encodes some files to higher bit depth).
- **Wrapper long-run session instability**: [#52](https://github.com/WorldObservationLog/wrapper/issues/52) — after ~400 ALAC songs all decrypts fail with "Invalid CKC error"; maintainer: "This is an Apple Music restriction that cannot be bypassed. Consider using wrapper-manager or other wrapper management tools" (i.e., restart/rotate instances). Similar: [#35](https://github.com/WorldObservationLog/wrapper/issues/35) (dies after 200-250 songs), [#26](https://github.com/WorldObservationLog/wrapper/issues/26) (crash when >1 device plays), several closed "Invalid CKC" reports ([#16](https://github.com/WorldObservationLog/wrapper/issues/16), [#29](https://github.com/WorldObservationLog/wrapper/issues/29), [#36](https://github.com/WorldObservationLog/wrapper/issues/36)); token-robustness PRs still open: [#53 "fix: improve token recovery and cache handling"](https://github.com/WorldObservationLog/wrapper/pull/53), [#62 "daemon: replace exit(1) callbacks with recoverable state machine"](https://github.com/WorldObservationLog/wrapper/pull/62); auth issues: [#44 "Login required: MUSIC_TOKEN not found"](https://github.com/WorldObservationLog/wrapper/issues/44) (open), [#65 2FA/token login request](https://github.com/WorldObservationLog/wrapper/issues/65) (closed).
- **Atmos**: [#30 "Not true Atmos"](https://github.com/WorldObservationLog/wrapper/issues/30) — closed as working-as-intended (reporter's ffprobe lacked JOC; maintainer showed full `eac3 (Dolby Digital Plus + Dolby Atmos)` output); open [#122 "Error … 2 when decrypting ec3 songs"](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/122) (EC-3 decrypt failure on the v2 stack); suggestion [#118](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/118) (multiple codecs in one M4A); 5.1 duration handling [#56](https://github.com/WorldObservationLog/wrapper/issues/56) (closed).
- **Lyrics**: open [#127 "401 error about lyrics"](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/127) (v2 gRPC stack, wrapper-side lyric API rejection); [#75 pronunciation request](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/75) (closed; shipped as `lyricsExtra`), PR [#90 translation replacement](https://github.com/WorldObservationLog/AppleMusicDecrypt/pull/90) (closed).
- **Platform**: [#61 Apple Silicon QEMU crash](https://github.com/WorldObservationLog/wrapper/issues/61) (open — see above); arm64 journey: [#57 request → closed](https://github.com/WorldObservationLog/wrapper/issues/57), [#8/#38/#31 arm64 build/run breakage](https://github.com/WorldObservationLog/wrapper/issues/38); Windows packaging: [#48 out-of-box build broken](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/48) (closed), [#72](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/72), macOS usage [#82](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/82).

## Fit-for-Waves verdict

**Adopt: wrap `wrapper@lite` as a local HTTP sidecar + `AppleMusicDecrypt@v3` (pinned commit) as the Apple provider engine.** Reasons:

1. It is the only actively maintained, license-clean (AGPL-3.0/MIT) stack in this lineage that meets every settled Waves constraint: one-time login with 2FA on the wrapper side; ALAC up to 24/192; Atmos (`ec3`) as an independent codec choice; lyrics in LRC/TTML/word-timed/translation/pronunciation; 5000×5000 cover art; runs on macOS/Windows/Linux via QEMU or Docker with the downloader itself being portable Python.
2. v3's shape is ideal for embedding: JSON-HTTP sidecar + local decryption + pure-Python muxing, with resume, batch, integrity checks, and an experimental self-hosting QEMU launcher Waves can mirror.
3. The known failure modes are documented and mitigable at the app level (restart/rotate the wrapper on `Invalid CKC`; treat integrity failures as retryable; handle the benign bit-depth mismatch).

Waves must add on top: a **search layer** (engine has none — use the public iTunes Search API or the catalog API with the wrapper's tokens), **wrapper lifecycle management** (sidecar supervision + login wizard + restart/cooldown), and **pinned builds** (no formal lite releases; pin commits and build via Waves' CI).

## Top three risks

1. **macOS Apple silicon runs emulated, and it's the least-proven path.** The decryption core is x86-64 Android code, so Apple silicon hosts go through QEMU TCG or Docker/Rosetta, where the flagship open bug [#61](https://github.com/WorldObservationLog/wrapper/issues/61) lives (signal 11 after 2FA). Mitigation: first-class login wizard + health checks around the sidecar, test early on M-series, consider a native aarch64 Android-lib build of `lite` upstream as a follow-up.
2. **Apple throttles long wrapper sessions.** After ~200-400 songs in one session, decrypts fail with "Invalid CKC" and the maintainer says it cannot be bypassed — only restarted/rotated ([#52](https://github.com/WorldObservationLog/wrapper/issues/52), [#35](https://github.com/WorldObservationLog/wrapper/issues/35)). Waves' long-playlist batch jobs must implement wrapper restart, cooldown/backoff, and task resumption.
3. **Upstream churn + intermittent integrity failures.** v3 is pre-1.0 and fast-moving (TUI rewrite commits daily), lite prebuilts are CI artifacts rather than releases, and "did not pass integrity check" failures are a persistent intermittent class with upstream-vs-source ambiguity (FAQ + [#58](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/58), [#53](https://github.com/WorldObservationLog/AppleMusicDecrypt/issues/53)). Mitigation: pin exact commits, wrap the engine behind Waves' own provider interface, retry integrity failures, and never partially save a failed file (already Waves' behavior).

Secondary (not in the top three but worth tracking): no search support (build Waves-side); device-spoofing engines are inherently cat-and-mouse with Apple — budget for upstream breakage response.
